What AIP-C01 actually tests

It's not enough to invoke a model. You need to know how to turn a business case into a GenAI application that is secure, observable, cost-efficient, and verifiable.

  1. Does the model already know what's needed? If not, add current data with RAG; if its underlying behavior must change, consider customization/fine-tuning.
  2. What quality level is required? Define evaluation, criteria, test data, and human review where it applies.
  3. What can fail or be abused? Apply controls to inputs, retrieval, tools, and outputs.
  4. How is it operated? Measure tokens, latency, errors, retrieval quality, and cost.
Exam pattern: requirement → architecture → control → metric. Example: "answer with current internal documents and citations" → RAG + vector store/Knowledge Base + per-document access control + retrieval evaluation.

Trap: don't use fine-tuning just so the model "knows" documents that change. RAG is usually faster to update and maintain.
RAG explained as a production flow

Ingestion: documents → validation/cleanup → segmentation (chunking) → embeddings → vector index. Query: question → embedding → search → optional filter, hybrid search, and reranking → context → FM → response with source.

  • Chunking: chunks that are too large add noise and raise token usage; too small loses context. Adjust to the document's structure and type.
  • Metadata: attributes like tenant, region, date, and permission. Used to filter before retrieval and prevents leakage between users.
  • Hybrid search: combines semantic matching with keywords. Reranking: reorders results to improve relevance.
  • Refresh: CDC/events or a scheduled refresh; monitor ingestion, the index, and retrieval quality.
Hint: "filter results by department or user" → metadata + access control in retrieval, not just a prompt saying "don't show that data."
Choosing and operating foundation models
  • Select based on quality for your use case, latency, cost per token, context window, modality, and region/compliance requirements.
  • Design a fallback to another model and retries with backoff for resilience. The fallback path must be evaluated, not just exist.
  • Use Bedrock to consume managed models and capabilities; use SageMaker when the model lifecycle and deployment need more control.

Domain 2 · Implementation and integration 26%

Agents, tools, and humans
  • Agent: an FM that chooses steps and uses tools to complete an objective. It is not simply a chatbot.
  • Tool: a function/API with a clear contract, input validation, and least-privilege permissions. Lambda is commonly used to encapsulate an action.
  • Human-in-the-loop: a person approves or corrects high-impact actions before they execute.
  • Step Functions: orchestrates states, retries, waits, and approvals; don't delegate all control to the FM.
  • MCP: a pattern/protocol for giving models consistent access to tools and context; governs which tools are exposed.
Trap: a model should never get broad permissions just because it "needs autonomy." Limit tools, actions, and data by role/policy.

Prompts as a software component

Version your prompts, use templates with variables, and test them against a set of cases. A prompt is production configuration: it requires review, traceability, and rollback. Prompt Flows lets you orchestrate stages; Prompt Management helps centralize versions.

After inferenceToxic output, invalid format, or hallucinationGuardrails, schema validation, citations, and business rules.
  • Prompt injection/jailbreak: an attempt to alter instructions or exfiltrate data. Treat the user's prompt as untrusted input.
  • PII: detect it, mask it, limit retention, and avoid logging sensitive data without need.
  • Auditing: CloudTrail for API activity; structured logging with secrets/PII redaction.
Accountability and compliance
  • Transparency: communicate limits, show sources when using RAG, and log relevant decisions.
  • Fairness: test results with representative sets; don't assume a model is neutral.
  • Governance: model cards, data lineage, tags, SCPs, and organizational controls.
  • Guardrails: filter content and PII, but don't replace IAM, encryption, evaluation, or application validation.

Domain 4 · Efficiency and optimization 12%

Cost, latency, and throughput
  • Tokens: reduce them with concise prompts, relevant context, output limits, and history summarization. More context doesn't always mean better quality.
  • Model: route simple tasks to the cheaper model; reserve expensive models for tasks that need them.
  • Cache: reuse results for repeated queries and avoid unnecessary invocations; consider invalidation and privacy.
  • Throughput: batch for non-urgent jobs, controlled concurrency, SQS as a buffer, and Provisioned Throughput when predictable demand justifies the commitment.
  • RAG: measure recall/relevance against latency. Pre-filtering metadata, tuning the index, and reranking all have trade-offs.
Hint: "reduce cost without degrading repeated responses" → cache. "steady, high, and predictable load" → evaluate Provisioned Throughput.
Observability that matters

Measure end-to-end latency, retrieval time, input/output tokens, errors/throttling, cost, throughput usage, retrieval quality, hallucinations, and prompt/embedding drift. CloudWatch centralizes metrics and alarms; X-Ray helps find which segment of the request is creating the latency.

Domain 5 · Testing, validation, and troubleshooting 11%

Evaluate before and after deployment
  • Build an evaluation dataset with normal cases, edge cases, security cases, and expected answers/rubric.
  • Evaluate model, prompt, retrieval, and agent separately; if everything is tested as one black box, you won't know what failed.
  • Use automated evaluation, human review, and, where useful, LLM-as-a-judge with controls. None of these replaces all the others.
  • Roll out gradually: canary/shadow, quality gates, monitoring, and rollback.
Hint: "poor RAG result" → first separate: did it fail to retrieve the right document, or did the FM fail to use it correctly?
