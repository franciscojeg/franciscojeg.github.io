Cómo razonar una pregunta SAA-C03

El examen evalúa diseño. Primero encuentra el requisito; después escoge el servicio. Una opción puede funcionar y aun así no ser la mejor.

  1. Subraya el objetivo: disponibilidad, lectura, baja latencia, desacoplamiento, privacidad, recuperación o costo.
  2. Localiza la restricción: MOST cost-effective, LEAST operational overhead, MINIMUM changes, lowest latency.
  3. Descarta por incompatibilidad: no elijas Multi-AZ para escalar lectura, ni una NAT Gateway para acceder privadamente a S3.
  4. Valida las capas: identidad, red, cómputo, datos, HA/DR y costo.
Regla de oro: requisito → patrón → servicio. No memorices “la respuesta C”; cambia un detalle del escenario y la arquitectura correcta puede cambiar.

AWS Well-Architected Framework

Es una guía para evaluar si una arquitectura está bien diseñada. Piensa en ella como la inspección de una casa: una aplicación puede funcionar hoy, pero también debe ser segura, resistir fallas, rendir bien, costar lo justo, ser operable y usar recursos responsablemente.

Importante: AWS actualmente define seis pilares. Si ves una guía que muestra cinco, probablemente omitió Sostenibilidad.
PilarPropósito, en palabras simplesPista típica en una preguntaEjemplo
Excelencia operacionalOperar, observar y mejorar el sistema de forma continua.Monitorear, automatizar despliegues, responder a incidentes.Alarma de CloudWatch y despliegue repetible con Infrastructure as Code.
SeguridadProteger identidades, accesos, sistemas y datos.Permisos, cifrado, MFA, secretos, auditoría.IAM Role en lugar de access keys guardadas en código.
ConfiabilidadSeguir funcionando o recuperarse cuando algo falla.Failover, Multi-AZ, backups, disaster recovery.ALB y Auto Scaling en más de una AZ.
Eficiencia de rendimientoUsar los recursos correctos para responder rápido y escalar.Latencia, throughput, caché, volumen de tráfico.CloudFront o ElastiCache para reducir latencia.
Optimización de costosEntregar lo necesario sin pagar por desperdicio.Most cost-effective, right-sizing, recursos sin uso.Lifecycle de S3 para datos que se consultan poco.
SostenibilidadReducir consumo de recursos y el impacto ambiental.Uso eficiente, apagar recursos o cargas intermitentes.Dimensionar instancias correctamente o usar serverless cuando corresponde.
Cómo usarlo en el examen: identifica la prioridad que la pregunta destaca. Varias opciones pueden apoyar distintos pilares, pero una decisión de Multi-AZ apunta principalmente a Confiabilidad; mover objetos de S3 a una clase fría apunta principalmente a Optimización de costos.

Dominio 1 · Arquitecturas seguras 30%

Enfócate: IAM, VPC, cifrado y acceso entre cuentas. Es el dominio con mayor peso.

IAM, STS y acceso entre cuentas
Crítico
  • Role: credenciales temporales para AWS services, workloads y acceso cross-account. Evita access keys en EC2/Lambda/ECS.
  • Trust policy define quién puede asumir el role; la policy de permisos define qué hace una vez asumido.
  • Para S3 cross-account, revisa identidad/role, bucket policy y, si aplica, la key policy de KMS. Un SCP puede limitar aunque IAM permita.
  • Principio: menor privilegio, MFA donde corresponda y secretos fuera del código.
Pista: “aplicación en cuenta A debe acceder a recurso de cuenta B” → role cross-account + trust policy + resource policy.
Trampa: una policy adjunta al usuario no sustituye una trust policy para asumir un role.
Red privada: VPC, SG, NACL y endpoints
Crítico
NecesidadRespuesta que debes reconocer
Instancia privada sale a internetNAT Gateway en subred pública + ruta desde subred privada.
Acceder a S3/DynamoDB sin internetGateway VPC Endpoint; para muchos otros servicios, Interface Endpoint/PrivateLink.
Control por instancia, retorno automáticoSecurity Group: stateful, solo reglas allow.
Filtrar tráfico por subred, permitir/denegar explícitamenteNACL: stateless; reglas inbound y outbound.
Conexión on-premises privada y consistenteDirect Connect; Site-to-Site VPN para túnel cifrado sobre internet.
Trampa recurrente: una NACL es stateless: si permites entrada, también debes permitir explícitamente el tráfico de retorno.
Cifrado, secretos y protección
  • KMS gestiona claves; para secretos con rotación nativa usa Secrets Manager. Parameter Store encaja para parámetros/configuración y secretos más simples.
  • En tránsito: TLS. En reposo: KMS y cifrado propio del servicio. Evalúa siempre permisos para usar la clave, no solo permisos sobre el recurso.
  • CloudTrail registra actividad API; Config evalúa configuración/cumplimiento; GuardDuty detecta amenazas; WAF protege apps HTTP(S).
Pista: “rotar automáticamente credenciales de base de datos” → Secrets Manager, no Parameter Store.

Dominio 2 · Arquitecturas resilientes 26%

Enfócate: eliminar puntos únicos de falla, Multi-AZ, desacoplar y elegir la estrategia de recuperación correcta.

Alta disponibilidad y escalado
  • ALB + Auto Scaling Group en varias AZ es el patrón web clásico. ELB distribuye; ASG reemplaza/escala instancias.
  • Una aplicación debe ser stateless: sesiones y archivos no deben vivir solo en el disco de la instancia. Usa DynamoDB/ElastiCache para sesión, S3/EFS según el caso.
  • Route 53 dirige DNS y health checks; failover routing ayuda a activar el sitio secundario.
Pista: “si falla una AZ, la aplicación debe seguir disponible” → componentes en múltiples AZ, no solamente backups.
RDS, Aurora y DynamoDB
RequisitoElecciónNo confundas
HA relacional, failover automáticoRDS Multi-AZNo escala lecturas; la standby no se usa para lectura.
Más capacidad de lecturaRead ReplicasReplicación asíncrona; no reemplaza Multi-AZ.
Relacional, alta performance/HA administradaAuroraAurora Replicas, Global Database y Serverless dependen del escenario.
NoSQL, baja latencia y escala masivaDynamoDBModela partition/sort key; DAX es caché para lecturas.
Trampa: “Multi-AZ” responde a disponibilidad; “read replica” responde a lectura. Lee cuál pide el escenario.
Mensajería y recuperación ante desastres
  • SQS desacopla productor y consumidor; visibility timeout evita procesamiento simultáneo; DLQ conserva fallos.
  • SNS publica a múltiples suscriptores; SNS + varias SQS es fan-out.
  • EventBridge enruta eventos por reglas e integra servicios/SaaS; Step Functions orquesta pasos, reintentos y estados.
  • DR: backup/restore es más barato y lento; pilot light y warm standby reducen RTO; active-active multi-region da máxima continuidad y mayor costo/complejidad.
Pista: “picos de solicitudes, consumidores procesan a distinto ritmo” → SQS como buffer. “Un evento debe llegar a varios sistemas” → SNS + SQS.

Dominio 3 · Alto rendimiento 24%

Storage: identifica el tipo de dato y el patrón de acceso
ServicioCuándo pensar en él
S3Objetos, data lake, estáticos, durabilidad masiva. Versioning, lifecycle, replication y CloudFront son asociaciones clave.
EBSBloques para una EC2; persistencia por AZ. gp3 como SSD general; io2 cuando IOPS/provisión crítica.
EFSFilesystem NFS compartido para Linux y múltiples instancias/AZ; crece automáticamente.
FSxFilesystem especializado (Windows, Lustre, NetApp, OpenZFS) según protocolo/workload.
Pista: “varias EC2 Linux necesitan el mismo filesystem” → EFS. “contenido web global cacheable” → S3 + CloudFront.
Compute, containers y serverless
  • EC2: selecciona familia por CPU (C), memoria (R/X), GPU (P/G) o I/O. Spot para tolerancia a interrupción; Savings Plans/RI para uso predecible.
  • Lambda: eventos, ejecución corta y sin administrar servidores. No la fuerces si el trabajo es prolongado o necesita entorno persistente.
  • ECS es orquestación AWS-native; Fargate elimina administración de hosts. EKS cuando Kubernetes/portabilidad/ecosistema K8s es requisito real.
  • Batch para jobs batch; ASG para capacidad de EC2 elástica.
Red y entrega de contenido
ServicioReconócelo cuando veas
CloudFrontCDN, caché HTTP(S), contenido estático o dinámico desde edge.
Global AcceleratorMejorar ruta/red global a endpoints; IP estáticas anycast, no es una caché.
ALBHTTP/HTTPS, routing por host/path, microservicios.
NLBTCP/UDP/TLS, alto throughput/baja latencia, IP estática.
Trampa: ambos CloudFront y Global Accelerator usan edge, pero solo CloudFront cachea contenido.

Dominio 4 · Optimización de costos 20%

El costo aparece en todos los dominios: si el enunciado dice “most cost-effective”, elimina sobreaprovisionamiento y operación innecesaria.

  • Compute: On-Demand si la carga es incierta; Spot para cargas tolerantes a interrupción; Savings Plans/RI para compromiso estable. Right-sizing con Compute Optimizer.
  • S3: lifecycle según frecuencia de acceso; Intelligent-Tiering cuando el patrón es impredecible. Recuerda retrieval/minimum storage duration al comparar clases frías.
  • Datos: serverless/on-demand para cargas variables; autoscaling y caché para evitar capacidad o lectura innecesaria.
  • Red: CloudFront reduce transferencia y solicitudes al origen; VPC endpoints pueden evitar NAT Gateway para tráfico a AWS.
  • Gobierno: Budgets alerta/protege; Cost Explorer analiza tendencias; tags habilitan asignación de costos.
Hábito de laboratorio: crea un Budget, revisa regiones y elimina NAT Gateways, LBs, EIPs, snapshots, EBS y RDS que no uses.

Servicios que no debes confundir

ParDecisión rápida
SQS vs SNSSQS = cola/buffer y consumidor; SNS = publicación a muchos destinos. Combínalos para fan-out.
NAT Gateway vs VPC EndpointNAT = salida desde privado a internet; endpoint = acceso privado a AWS/PrivateLink.
Multi-AZ vs Read ReplicaHA/failover vs escala de lectura.
CloudFront vs Global AcceleratorCDN/caché vs aceleración de red a endpoints.
DataSync vs Storage GatewayTransferencia/migración de datos vs acceso híbrido continuo a storage AWS.
Secrets Manager vs Parameter StoreRotación y ciclo de secretos vs parámetros/configuración económicos.
Security Group vs NACLInstancia y stateful vs subred y stateless.
