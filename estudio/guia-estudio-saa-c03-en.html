How to reason through a SAA-C03 question

The exam evaluates design. First find the requirement, then choose the service. An option can work and still not be the best one.

  1. Underline the goal: availability, read scaling, low latency, decoupling, privacy, recovery, or cost.
  2. Locate the constraint: MOST cost-effective, LEAST operational overhead, MINIMUM changes, lowest latency.
  3. Eliminate by incompatibility: don't pick Multi-AZ to scale reads, or a NAT Gateway to reach S3 privately.
  4. Validate the layers: identity, network, compute, data, HA/DR, and cost.
Golden rule: requirement → pattern → service. Don't memorize "answer C"; change one detail in the scenario and the correct architecture can change.

AWS Well-Architected Framework

It's a guide for evaluating whether an architecture is well designed. Think of it like a home inspection: an application can work today, but it should also be secure, resilient to failure, perform well, cost what it should, be operable, and use resources responsibly.

Important: AWS currently defines six pillars. If you see a guide showing five, it probably dropped Sustainability.
PillarPurpose, in plain wordsTypical clue in a questionExample
Operational ExcellenceRun, observe, and continuously improve the system.Monitoring, automating deployments, responding to incidents.A CloudWatch alarm and a repeatable deployment with Infrastructure as Code.
SecurityProtect identities, access, systems, and data.Permissions, encryption, MFA, secrets, auditing.An IAM Role instead of access keys stored in code.
ReliabilityKeep running, or recover, when something fails.Failover, Multi-AZ, backups, disaster recovery.An ALB and Auto Scaling across more than one AZ.
Performance EfficiencyUse the right resources to respond fast and scale.Latency, throughput, caching, traffic volume.CloudFront or ElastiCache to cut latency.
Cost OptimizationDeliver what's needed without paying for waste.Most cost-effective, right-sizing, unused resources.An S3 lifecycle policy for rarely accessed data.
SustainabilityReduce resource consumption and environmental impact.Efficient usage, shutting down idle or intermittent workloads.Right-sizing instances or using serverless where it fits.
How to use it on the exam: identify the priority the question highlights. Several options can support different pillars, but a Multi-AZ decision points mainly to Reliability; moving S3 objects to a cold storage class points mainly to Cost Optimization.

Domain 1 · Secure architectures 30%

Focus on: IAM, VPC, encryption, and cross-account access. It's the highest-weighted domain.

IAM, STS, and cross-account access
Critical
  • Role: temporary credentials for AWS services, workloads, and cross-account access. Avoid access keys on EC2/Lambda/ECS.
  • A trust policy defines who can assume the role; the permissions policy defines what it can do once assumed.
  • For cross-account S3, check the identity/role, the bucket policy, and, if applicable, the KMS key policy. An SCP can restrict access even when IAM allows it.
  • Principle: least privilege, MFA where appropriate, and secrets kept out of code.
Clue: "an application in account A must access a resource in account B" → cross-account role + trust policy + resource policy.
Trap: a policy attached to a user doesn't substitute for a trust policy when assuming a role.
Private networking: VPC, SG, NACL, and endpoints
Critical
NeedAnswer you should recognize
A private instance needs outbound internet accessNAT Gateway in a public subnet + a route from the private subnet.
Access S3/DynamoDB without internetGateway VPC Endpoint; for most other services, an Interface Endpoint/PrivateLink.
Instance-level control, automatic return trafficSecurity Group: stateful, allow rules only.
Filter traffic by subnet, explicitly allow/denyNACL: stateless; inbound and outbound rules.
Private, consistent on-premises connectionDirect Connect; Site-to-Site VPN for an encrypted tunnel over the internet.
Recurring trap: a NACL is stateless — if you allow inbound traffic, you must also explicitly allow the return traffic.
Encryption, secrets, and protection
  • KMS manages keys; for secrets with native rotation use Secrets Manager. Parameter Store fits simpler parameters/configuration and secrets.
  • In transit: TLS. At rest: KMS and the service's own encryption. Always check permissions to use the key, not just permissions on the resource.
  • CloudTrail logs API activity; Config evaluates configuration/compliance; GuardDuty detects threats; WAF protects HTTP(S) apps.
Clue: "automatically rotate database credentials" → Secrets Manager, not Parameter Store.

Domain 2 · Resilient architectures 26%

Focus on: eliminating single points of failure, Multi-AZ, decoupling, and choosing the right recovery strategy.

High availability and scaling
  • ALB + Auto Scaling Group across multiple AZs is the classic web pattern. The ELB distributes traffic; the ASG replaces/scales instances.
  • An application should be stateless: sessions and files shouldn't live only on an instance's disk. Use DynamoDB/ElastiCache for session state, S3/EFS depending on the case.
  • Route 53 handles DNS and health checks; failover routing helps bring up the secondary site.
Clue: "if an AZ fails, the application must stay available" → components across multiple AZs, not just backups.

Messaging and disaster recovery
  • SQS decouples producer and consumer; the visibility timeout prevents duplicate processing; a DLQ preserves failures.
  • SNS publishes to multiple subscribers; SNS + several SQS queues is fan-out.
  • EventBridge routes events by rules and integrates services/SaaS; Step Functions orchestrates steps, retries, and state.
  • DR: backup/restore is cheaper and slower; pilot light and warm standby reduce RTO; active-active multi-region gives maximum continuity at higher cost/complexity.
Clue: "request spikes, consumers process at different rates" → SQS as a buffer. "One event must reach several systems" → SNS + SQS.

Domain 3 · High performance 24%

Storage: identify the data type and access pattern
ServiceWhen to think of it
S3Objects, data lake, static assets, massive durability. Versioning, lifecycle, replication, and CloudFront are the key associations.
EBSBlock storage for a single EC2 instance; persists per AZ. gp3 as general-purpose SSD; io2 when IOPS/provisioning is critical.
EFSShared NFS filesystem for Linux and multiple instances/AZs; grows automatically.
FSxSpecialized filesystem (Windows, Lustre, NetApp, OpenZFS) depending on protocol/workload.
Clue: "several Linux EC2 instances need the same filesystem" → EFS. "cacheable global web content" → S3 + CloudFront.
Compute, containers, and serverless
  • EC2: pick a family by CPU (C), memory (R/X), GPU (P/G), or I/O. Spot for interruption-tolerant workloads; Savings Plans/RI for predictable usage.
  • Lambda: event-driven, short execution, no server management. Don't force it if the job is long-running or needs a persistent environment.
  • ECS is AWS-native orchestration; Fargate removes host management. Use EKS when Kubernetes/portability/the K8s ecosystem is a real requirement.
  • Batch for batch jobs; ASG for elastic EC2 capacity.
Networking and content delivery

ALBHTTP/HTTPS, host/path-based routing, microservices.

Trap: both CloudFront and Global Accelerator use the edge, but only CloudFront caches content.

Domain 4 · Cost optimization 20%

Cost shows up in every domain: if the question says "most cost-effective," eliminate over-provisioning and unnecessary operations.

  • Compute: On-Demand for uncertain load; Spot for interruption-tolerant workloads; Savings Plans/RI for a stable commitment. Right-size with Compute Optimizer.
  • S3: lifecycle policies based on access frequency; Intelligent-Tiering when the pattern is unpredictable. Remember retrieval/minimum storage duration when comparing cold storage classes.
  • Data: serverless/on-demand for variable load; autoscaling and caching to avoid unnecessary capacity or reads.
  • Network: CloudFront reduces transfer and requests to the origin; VPC endpoints can avoid a NAT Gateway for traffic to AWS.
  • Governance: Budgets alerts/protects; Cost Explorer analyzes trends; tags enable cost allocation.
Lab habit: create a Budget, review regions, and remove any NAT Gateways, load balancers, EIPs, snapshots, EBS volumes, and RDS instances you're not using.

Multi-AZ vs Read ReplicaHA/failover vs read scaling.
CloudFront vs Global AcceleratorCDN/caching vs network acceleration to endpoints.

Secrets Manager vs Parameter StoreSecret rotation and lifecycle vs cost-effective parameters/configuration.
